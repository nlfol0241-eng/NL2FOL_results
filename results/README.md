# Z3 Equivalence Results: Gold FOL vs. LLM-Predicted FOL

This repository holds the results of checking whether **LLM-predicted first-order logic (FOL)** formulas are **logically equivalent** to the **gold FOL** formulas for Spider text-to-SQL questions. The checks use the Z3 SMT solver.

Each formula is a multi-sorted FOL translation of a natural-language question over a database schema. Two formulas count as equivalent if they are equivalent **modulo the schema's sort axioms and key/foreign-key axioms**.

## Pipeline Overview

```
inputs/example_<id>.json
        │
        ▼   Generation (stages G1, G2, G3, ...)
        │     load input → build signature → tokenize & parse → ... → emit Z3 script
        │
        ├── generation error ──► recorded in logs/ and errors.json (no check script)
        │
        ▼
checks/equiv_check_<id>.py
        │
        ▼   Check run (stages R1–R4)
        │     assemble background → gold ⊨ predicted → predicted ⊨ gold → verdict
        │
        ├── check error ──► recorded in logs/ and errors.json
        │
        ▼
VERDICT: EQUIVALENT | NOT EQUIVALENT | UNKNOWN  ──► results.json / results.csv / summary.txt
```

Errors can occur at **two levels**:

1. **Generation error:** the input cannot be turned into a Z3 script, for example because the predicted FOL cannot be parsed. **No** `equiv_check_<id>.py` file is created for that example.
2. **Check error:** the Z3 script was generated, but running it failed, for example because of a Z3 exception at run time.

## Folder and File Descriptions

### `inputs/`: one JSON specification per example

`example_<id>.json` holds everything needed to check one NL query:

| Key | Description |
|---|---|
| `id` | Example identifier (matches `equiv_check_<id>.py`). |
| `NL` | The natural-language question. |
| `Vocabulary` | Predicates (tables), functions, and constants used in the formulas. |
| `Arity` | The **local sort** of every predicate column, function argument, and constant. For example, `singer(Singer_ID, Name, Country, ...)` and `"20": "Age"`. |
| `Axioms` | Schema-level FOL axioms: **primary-key** (functional dependency) and **foreign-key** (inclusion) constraints. |
| `Internal Symbols` | Mapping from internal symbols (`A`, `A0`, `A1`, …, `const1`) to schema names. |
| `Gold FOL` | Reference formula (`string`) and its free (answer) variables (`free vars`, e.g. `c : Country`). |
| `Gold FOL internal` | The gold formula in internal symbols, with the relational algebra (`RA`, `Processed_RA`), relational calculus (`RC`), free variables, `db_id`, and `processed_sql` it was derived from. |
| `Global Sorts` | SQL-level types used by the schema (for example `int`, `bool`, `text`, `varchar(60)`, `numeric(10,2)`). |
| `Sort Axioms` | Per table, the global sort of each local sort (for example `Age = int`, `Country = text`). |
| `Additional info` | The original Spider SQL query. |
| `Predicted FOL` | The LLM-generated formula (`string`) and its free variables (`free vars`). |

### `checks/`: generated Z3 equivalence scripts

`equiv_check_<id>.py` is created **only for inputs that generated without error**. It is auto-generated by `fol_equiv_gen.py`, so do not edit it by hand. Each script is self-contained and can be run directly:

```bash
python checks/equiv_check_0.py              # prints the verdict
python checks/equiv_check_0.py -v           # stage summaries
python checks/equiv_check_0.py -vv          # full detail
python checks/equiv_check_0.py --log run.log --timings
```

**How the check works**

- **Sorts:** each local sort (such as `Age`, `Country`) is an alias of its global sort. Each global sort maps to a Z3 built-in sort (`Int`, `Real`, `String`, `FP`, `Bool`). Parameterised SQL types such as `varchar(60)` or `numeric(10,2)` add **domain constraints**.
- **Free variables:** the answer variables of the gold and predicted formulas are paired by sort and replaced by the **same fresh constants**. For example, gold `c` and predicted `y` both become `FV_Country_0`.
- **Equivalence:** the script checks that `Axioms → (Gold ↔ Predicted)` is valid. It does this by showing that both one-directional counterexample queries are **unsat**:
  - `R2`: `Gold ∧ ¬Predicted` (does gold entail predicted?)
  - `R3`: `Predicted ∧ ¬Gold` (does predicted entail gold?)
- **Skolemisation:** the leading existential prefix of the asserted side is replaced by named witnesses (`WGOLD_*`, `WPREDICTED_*`). This keeps counter-models readable.
- **Restarts:** queries that use strings and quantifiers can stall, so Z3 is retried on a fixed `(seed, timeout)` schedule. The timeouts are 2 s, 8 s, 30 s, and 120 s, each with seeds 0–3. This keeps results deterministic.
- **Order on sorts:** comparisons on sorts without a built-in order use uninterpreted relations. These are flagged in `undefined_orders` as needing a definition.

**Main sections of a generated script**

| Section | Content |
|---|---|
| Header comments | NL question, global → Z3 sorts, local-sort aliases, domain constraints |
| `P_<table>` | Z3 function declaration for each predicate (table) |
| `sort_axioms`, `axioms`, `order_axioms`, `uniqueness` | Background assertions |
| `free_vars`, `free_var_domains` | Shared answer variables |
| `gold_formula`, `gold_skolem`, `gold_witnesses` | Gold FOL encoding |
| `predicted_formula`, `predicted_skolem`, `predicted_witnesses` | Predicted FOL encoding |
| `localize_model`, `print_model` | Map a counter-model back to **local sorts** and print relations, domains, and joins |
| `main()` | Runs stages **R1–R4** and prints the verdict |

**Possible verdicts**

| Verdict | Meaning |
|---|---|
| `EQUIVALENT` | Both directions are `unsat`. |
| `NOT EQUIVALENT` | At least one direction is `sat`. A counter-model is printed in local sorts. |
| `UNKNOWN` | No direction was `sat`, and at least one direction stayed `unknown` after all restarts. |

### `logs/`: one log per example

Each log records the **generation stages** and, if a check was run, the **run stages**:

- Header: `input` path, `output` script path, and whether the check was run (`run`).
- Generation stages:
  - `[G1] load input`: reads the JSON and lists its sections.
  - `[G2] build signature`: global and local sorts, predicates, functions, and constants, with a warning count.
  - `[G3] tokenize and parse`: parses the gold and predicted FOL strings.
  - … the remaining generation stages up to emitting the script.
- Run stages: `[R1]` to `[R4]` (assemble background, the two entailment checks, and the verdict).
- Optional per-stage timings.
- On failure: a line such as `!! FAILED in stage [G3] tokenize and parse: SyntaxError: ...` followed by the full Python traceback.

> **Example generation error:** if a model writes its predicted FOL in LaTeX syntax (`\exists`, `\land`) instead of Unicode (`∃`, `∧`), parsing fails at `[G3]` with `SyntaxError: unexpected character '\\' at position 0`. No check script is created for that example.

### `errors.json`

Lists the examples that failed, either at **generation** (no check script) or at **check** time (script created but its run failed). For each example it records the failing stage and the error message, so failures can be grouped by cause (for example, parse errors in the predicted FOL).

### `results.json`

The per-example results for the model in machine-readable form: the example `id` with its verdict (`EQUIVALENT` / `NOT EQUIVALENT` / `UNKNOWN`) or its error status.

### `results.csv`

The same per-example results as `results.json`, in a flat table. Open it in Excel or pandas for filtering and analysis.

### `summary.txt`

A human-readable overview of the whole run for one model: the total number of examples and counts of equivalent, not equivalent, unknown, generation-error, and check-error cases. Use it for a quick comparison across models.

## Reproducing a Single Check

```bash
pip install z3-solver
cd z3_equivalence_results_gpt_6
python checks/equiv_check_0.py -v
```

Example output for an equivalent pair:

```
[gold |= predicted ?] unsat
[predicted |= gold ?] unsat

VERDICT: EQUIVALENT
```
